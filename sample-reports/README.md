# The reports a dealership would export

Sixteen CSVs — eight per outlet — regenerated by `pnpm run db:export-reports`.

> **Nothing in here is invented.** Every value is read out of the mirror this
> dealership already has. A second, made-up book would give the product two
> versions of one dealership, which is the failure it exists to fix.

They exist because OBJ-24 gave the product three ways in — `API`, `REPORT` and
`DOCUMENT` — and only the first has ever had anything to point at. There was no
file to drop, so the report path could be *verified* and could not be *used*.

## What is here

```
sample-reports/
  HMC-DL-0417/          Saraswati Automobiles, New Delhi — the working showroom
  HMC-MH-1182/          Deccan Two Wheelers, Mumbai — parked (R-43), a handful of rows
```

Both outlets carry the same eight, numbered in the order a dealership is
onboarded rather than alphabetically — you cannot make sense of an enquiry
register until you know who the sales executives are, or of a registration file
until you know which deal it belongs to.

| | | Saraswati |
|---|---|---|
| `01-vehicle-stock.csv` | what is standing on the floor, with what it cost and what it is costing | 97 |
| `02-staff-master.csv` | everybody, **including the ones who left** | 21 |
| `03-enquiry-register.csv` | customers, as leads, against the manufacturer's clock | 141 |
| `04-deal-register.csv` | sales — booking to invoice to delivery | 78 |
| `05-registration-register.csv` | RTO files, lodged and pending | 88 |
| `06-job-card-register.csv` | the workshop, against the promise made | 104 |
| `07-part-stock.csv` | spares on the shelf | 67 |
| `08-receivables.csv` | what the outlet is owed, party by party | 50 |

## Three rules that decided what may appear in them

**Mirror fields only, never decision fields.** A dealer's own system knows the
chassis number, the promised date and the invoice number. It has never heard of
`reassignedToEmpCode`, `customerInformedAt` or `rtoChasedAt` — those are what
*DDMS* concluded. A file claiming to come from the dealer while carrying them
would be the product reading its own output back as evidence, which is the
failure R-66 closes on the other side of the house.

**Their vocabulary, not ours.** `Deal No`, not `dealId`. The whole point of the
mapping is that a dealership's headings are theirs and a model is asked once
what they mean; headings that happened to match our column names would prove
nothing. On this shape all sixteen are placed by name and **no model is called
at all**.

**Their formats.** `dd/mm/yyyy`, `₹ 1,24,500.00`, `Y`/`N`, a title row above the
headings and a total row underneath. Both of those are things the parser has to
survive, and the total row is the one that once arrived as a deal priced at 78.

## Things in the data worth knowing before you read it

- **Policy numbers carry `SIM-`.** Every one is a policy no insurer issued
  (R-41), and the prefix is on *both* sides of the reconciliation — one side
  carrying it and the other not would manufacture a conflict per matched deal.
- **Staff who have left are in the file**, with a date of leaving. That is the
  whole orphaned-work premise: an enquiry assigned to somebody who left in
  February is on nobody's list and is late by no measure the DMS holds. An
  absent row is *not* a departure (R-62), which is why departures are stated
  rather than implied by omission.
- **Empty is not `N`.** A blank flag means nobody recorded it; `N` means it is
  known not to be the case. Collapsing them would hand the parser a certainty
  the dealer never had.
- **No dealer code column.** An export out of your own system does not repeat
  your own code on every row — the folder says which outlet it came from, and
  `syncDealerCode` supplies it.

## Feeding them in

```
POST /api/dms/ingest/report
{ "showroomId": 1, "dataType": "DEAL", "filename": "04-deal-register.csv", "text": "<the file>" }
```

The drop **parses and holds**; nothing reaches the mirror until a person
confirms what the columns mean. Dropping `04-deal-register.csv` returns:

```
batch 63  status=PENDING_MAPPING   mapping=PROPOSED  (already known: false, model used: false)
rows: 79 seen, 0 accepted, 0 rejected
headings: 16 read, 16 mapped
```

79 rather than 78 because the total row is a line in the file; it is rejected as
a record when the batch is released, with a reason, rather than skipped in
silence.

Then `POST /api/dms/ingest/mappings/{id}/confirm` releases every held batch on
that shape, and every file of the same shape afterwards is read by column
position with no model at all.

> **There is no screen for this yet.** The endpoint is complete and VeloDocs has
> the confirmation view; what is missing is the place a dealership drops the
> file. Until it exists these are driven over HTTP.

## Regenerating

```
pnpm run db:export-reports
```

Deterministic — no clock read, no random, every query sorted — so running it
twice writes byte-identical files. A diff means the dealership changed, not that
the exporter did.
